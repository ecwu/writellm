# R4 — 引擎中立 Main 产品权威

状态:设计稿
对应计划:`../implementation-plan.md` 第 8 节;`../target-architecture.md` 第 11.2 节
上游引用:纯仓库内部阶段,无 cordis/dsh 依赖。依据为现有实现
(`src/main/agent/mutation-service.ts`、`review-issue-service.ts`、`writing-task-service.ts`、
`change-set-batch-service.ts`、`section-proposal-refresh.ts`、`src/main/project/migrations/0016`–`0035`)

## 目标

把当前挂在 Pi 身份上的产品协作与提案权威,改造成引擎中立的产品服务,**不合并**两套
Harness 运行时。R4 之后,产品表(提案、评审问题、写作任务、模型审计、资产溯源)只认识
封闭的 `AgentOrigin` 引擎标签,不再直接引用 `agent_sessions` / `agent_runs` / `agent_events`。

这一阶段是整个过渡中**爆破半径最大**的一步:它在 Pi 仍是生产引擎时迁移活跃产品表。
它不依赖任何 Cordis 代码,允许独立排期(包括先于 R1),默认仍安排在 R3 之后。

## 背景问题

当前 schema 把产品协作权威绑死在 Pi 身份上:

| 表 | 建立迁移 | Pi 耦合点 |
| --- | --- | --- |
| `mutation_proposals` | 0016 | FK → `agent_sessions` / `agent_runs` / `agent_events`、`model_requests`、`section_revisions` |
| `review_issues` | 0029 | FK → sessions/runs、`mutation_proposals` |
| `agent_writing_tasks` | 0030(0031 给 runs 加 task FK) | 表名与 FK 均为 Pi 专有 |
| `model_requests` | 0009(0022 加 agent 溯源) | agent session/run/event FK |
| `manuscript_assets` / `section_revision_assets` | 0022 / 0035 | agent 溯源字段、资产变体提案引用 |
| `agent_change_set_commands` | 0032 | change-set 批量命令与 Pi 提案绑定 |

只要这些 FK 存在,Cordis 引擎的写工具(R6)就无法落地——模型不能选择 Main 必须绑定的
权威 ID,而 Cordis 会话又不是 `agent_sessions` 的行。

## 设计细节

### 1. AgentOrigin:封闭的引擎起源结构

```ts
interface AgentOrigin {
  engine: 'pi-legacy' | 'cordis'
  sessionId: string
  runId: string
  toolCallId?: string
}
```

- `engine` 是闭集枚举,新增引擎必须改类型并过评审;
- origin 只携带**标识符**,不构成对任何引擎会话表的 FK;引擎会话表的存在性由各自引擎
  保证,产品权威不做跨引擎引用完整性检查(否则会重新引入耦合);
- 存储形态:各产品表以 `origin_engine TEXT CHECK IN ('pi-legacy','cordis')` 加
  `origin_session_id`、`origin_run_id`、`origin_tool_call_id`(可空)四列表达,代替原 FK 列。

### 2. 表迁移方案(单次、前向、带备份与完整性校验)

遵循仓库现有迁移约定(备份 → 迁移 → `integrity_check` → 恢复覆盖),一次性完成:

| 迁移动作 | 说明 |
| --- | --- |
| `mutation_proposals` → `writing_change_proposals` | SQLite 表重建(建新表、拷贝、drop、rename),保留原提案 ID、决策、已应用结果、refresh 链(`section-proposal-refresh.ts` 的 lineage)与 writing task 关联;session/run/event FK 列改写为四列 origin,既有行打 `engine='pi-legacy'` |
| `agent_writing_tasks` → `writing_tasks` | 同上;`agent_runs.writing_task_id`(0031)的反向引用改为不带 FK 的普通列,由 Pi 自有逻辑维护可读性 |
| `review_issues` | session/run/proposal FK 列改写为 origin 四列 + 指向 `writing_change_proposals` 的引擎中立提案引用 |
| `model_requests` | 增加 `runtime_engine` 列与通用 session/run origin 列,去掉 Pi 会话 FK |
| `manuscript_assets` / `section_revision_assets` / 资产变体 | agent 溯源字段加引擎判别;变体的提案引用改指向 `writing_change_proposals` |
| `agent_change_set_commands` | 提案引用改指向 `writing_change_proposals`,命令本身的批量语义不变 |

规则:

- 只迁移**产品权威数据**;不复制、不转换、不解释任何 Pi 会话/事件数据;
- 迁移后不存在可写的旧影子表——`mutation_proposals` 等旧表在同一迁移中删除;
- 迁移在单个事务内完成,网络与 worker 等待不参与(架构 §11.3)。

### 3. 新的引擎中立 Main 服务(`src/main/agent-platform/`)

按架构 §20 的目录约定,新增引擎中立服务契约与实现:

```text
src/main/agent-platform/
  origins/         # AgentOrigin 类型、Zod schema、引擎标签校验
  proposals/       # writing_change_proposals 权威:create/decide/apply/undo/refresh、
                   # change-set 批量、image insert 执行
  review-issues/   # review issue 有界权威
  writing-tasks/   # 写作任务/步骤权威
  model-audit/     # model_requests 的引擎中立记录
```

- 服务契约与 Pi/Cordis 运行时类型零接触:输入是产品 ID + `AgentOrigin`,输出是产品事实;
- 乐观并发不变:源版本校验、状态机检查、undo/refresh lineage 语义从现有
  `mutation-service.ts` 原样移植,不改变产品行为;
- 事务边界不变:产品权威事务只含本地 SQLite 工作;引擎回调事件若不能同事务提交,
  走同事务提交的 durable outbox 行,幂等 drain(架构 §11.3);
- 服务模块不得 import 任一 Harness 运行时(import-boundary 测试机械执行)。

### 4. Pi Main adapter 改造

- `mutation-service.ts`、`review-issue-service.ts`、`writing-task-service.ts`、
  `change-set-batch-service.ts` 改为薄 adapter:把 Pi 会话/运行上下文翻译成 `AgentOrigin`
  (`engine='pi-legacy'`),调用 `agent-platform` 的新服务;
- Pi 的 worker、loop、会话事件、Renderer 转录一律不动;
- Pi 侧可见行为必须**逐字节不变**:现有全部提案/审批/undo/refresh/批量/评审/任务/图像/
  项目重开测试不改断言地通过。

### 5. 与 Cordis 的接口预留(本阶段不实现 Cordis 写工具)

- 新服务的 origin 校验接受 `engine='cordis'`,使 R6 可以直接接入;
- 用一个合成的 Cordis origin fixture(不产生 Cordis 运行)证明新权威可被第二引擎调用:
  创建/查询一个惰性提案,验证乐观并发与状态机与引擎无关。

## 测试计划

- **回归**:现有全部 Pi 提案、审批、undo、refresh、change-set 批量、review issue、
  writing task、图像、项目重开测试不改断言通过(`session-service.test.ts` 48 例、
  `mutation-service.test.ts` 19 例等);
- **迁移**:迁移前后行数/ID/决策/lineage 一致的快照比对;备份恢复后可正常打开;
  迁移中途失败(注入故障)不留下半迁移状态;
- **完整性**:每个恢复 fixture 过 `integrity_check` 与新 FK 检查;
- **引擎中立**:合成 Cordis origin 的创建/查询/乐观冲突/状态机路径;
- **边界**:扫描证明 `agent-platform` 无 Harness import、Cordis 表与 Pi 表互相无 FK。

## 验收门槛

- 上述测试全绿;`check:fast`、Electron 全套、`check:package`(schema 变更触发打包门);
- 两个引擎的提案可共存并按 origin 区分(R6 之后才有真实 Cordis 提案,本阶段用合成 fixture);
- 无双写:迁移后只有新服务写产品记录;
- 文档同步:`current-plan.md`、tracker、history 与 ADR 045 的后果清单。

## 回滚

前向恢复:还原迁移前的项目备份。**没有**活跃的双 schema 回退——这是刻意的,
迁移的备份/完整性/恢复覆盖就是回滚机制。

## 风险

| 风险 | 控制 |
| --- | --- |
| 迁移损坏活跃提案/评审/任务数据 | 最高爆破半径标注;备份 + 完整性 + 恢复 fixture;全套 Pi 回归为发布标准 |
| 表重建遗漏隐式依赖(索引、触发器、视图) | 迁移前后 schema diff 比对;恢复 fixture 覆盖 |
| origin 去 FK 化后悬挂引用难以排查 | origin 四列 + 引擎判别在查询接口强制;诊断查询列出无法解析的 origin |
| adapter 改造引入行为漂移 | 现有测试不改断言;golden 场景比对产品事实 |
