## 目标

引入**精确版本**的 Cordis 框架与可信组合基座,在任何产品功能代码累积之前,用
conformance 套件证明生命周期、事务化 reload、诊断与 correlation 契约。
R1 不暴露 Agent 会话 UI、不触碰 Pi 运行时、不做模型调用。

这是整个重构的地基:框架行为一旦凭假设而非凭测试建立,后续每个阶段都会在
上面累积错误。R1 的产出几乎全部是测试与基座代码。

## 设计细节

- 这些 npm 制品的 provenance 是 deepseek-harness 仓库的发布流程;若产品修复需要
  patch 框架,升级路径为 pnpm `patchedDependencies` 优先、vendor 其次,
  均连同 source diff 记录进依赖盘点;
- WriteLLM 代码**不** import 任何 DeepSeek Harness Agent 包(dsh-*),只采用框架;
- 框架升级是单独的架构维护变更,附 source diff 与 conformance 证据。

### 2. 可信组合基座(`src/main/cordis-agent/composition/`)

- **可信内置 catalog**:配置行只命名稳定 catalog ID,永不是任意 npm/文件系统模块
  specifier;catalog 把 ID 映射到静态打包、带版本的插件与其闭合 Zod config schema;
- **生产配置禁用 `!!js` 表达式求值**(评审轮决定):闭合 schema 下不需要插值,
  禁掉消除配置面的代码执行风险。框架事实:`!!js` 仅在 `config` 内部与 `disabled`
  字段受支持,且经 `with(ctx) eval` 在插件自己的 context 上求值——这正是必须
  在生产禁用的原因;
- **config schema 校验走 Standard Schema**:插件的静态 `Config` 须兼容
  Standard Schema(`~standard.validate` 且**同步**,async 校验被框架直接拒绝);
  闭合 Zod schema 经其 Standard Schema 兼容层接入,校验发生在依赖激活后
  (fork 的延迟解析),不是 `ctx.plugin()` 调用时;
- **生产配置只读**:loader 的写回行为(如插件自我 dispose 时把 `disabled = true`
  持久化回配置文件)在生产关闭;enable/disable 与配置状态存 app.sqlite,
  配置文件本身只读;
- **HMR 仅限开发构建**,且需要显式暴露 loader internals(框架要求
  `loader.internal`,否则 HMR 服务拒绝启动)与 timer 插件;生产装配不含此二者;
- **composition revision**:单调递增,附内容 hash 与 per-entry config hash;
- **事务化 reload**(fork 加固行为,逐条进 conformance):
  - `Entry.update()`:普通 config 先在旧 Fiber 上更新,失败恢复旧 config 再更新;
    更换 module/inject/group 时先卸载旧 Fiber、启动候选,失败则重新启动旧 plugin;
  - `EntryGroup.update()`:并发 settle 候选,任一失败删除新增项、按旧序恢复旧项;
  - `Include.refresh()`:detached candidate 解析与顶层校验,child tree 更新成功后
    才提交 content/data cache,失败保留上一棵树;
  - child-tree mutation 串行 queue;watcher 精确匹配文件;同路径突发刷新
    dirty+running 合并;dispose 时关闭 watcher 并 drain 全部 refresh 任务;
- **激活审计**:boot 后断言全部必需 Fiber 进入 ACTIVE;意外 PENDING/FAILED/缺失
  可见地上报(fail-loud,不是框架默认的静默等待);
- **boot 协调器**:内置 profile 层 + 项目 override 层,确定性 precedence;
  部分 boot 失败时 dispose 已建部分树。

### 3. 最小 file-backed prompt contribution fixture

一个内置 catalog 条目,把某个文件内容装配为 prompt contribution:

- 有效编辑 → 校验通过 → composition revision 推进 → 新内容生效(**无模型调用**);
- 无效编辑 → 保留 last-good 贡献 → 诊断显示失败阶段(parse/validate/apply);
- 快速连续编辑 → 串行合并,不交错;
- 这是 R5 文件背书 instructions/Skills 的先行证明。

### 4. 测试 Context 工厂

- Main 测试 Context 与 worker 测试 Context 的最小工厂(真实 cordis,无 Electron);
- 供 R2+ 的全部插件测试复用;不放任何产品服务。

### 5. 只读 inventory 投影

直接从 live Loader/Fiber registry 投影(**不维护第二份生命周期真相**,dsh
plugin-inventory 同款原则):稳定 entry ID、catalog/plugin ID 与版本、effective
enablement、scope、composition/config revision、Fiber phase、required/provided
services、上次激活与 teardown 时长、上次 reload 结果。R2 把它接到诊断 UI。

### 6. Correlation/trace 契约

- trace/parent ID 与 flags 的契约 + AsyncLocalStorage 传播 helper;
- **不建** span 模型、sink、trace UI(延期决策,架构 §19.1);
- 契约保证:标识符丢失或缺位永不改变 fixture 结局或 disposal。

### 7. Runtime-invariant companion

- companion 发现机制(包可发布 `./invariant` 伴生模块,dsh runtime-diagnostics 形态);
- 一个 request/composition invariant fixture:在真实插件图上可执行地检查
  "reload 只在 settle 后推进 revision"之类的契约;debug 构建装全量,生产装有界子集。

### 8. Import-boundary 机械执行(计划 §3,首个实现提交即生效)

```text
Cordis roots   -> 只可 import 共享 Cordis 契约与引擎中立平台
Legacy roots   -> 只可 import legacy 契约与引擎中立平台
Engine shell   -> 只可 import opaque Renderer entry 与 tagged summary
Product platform -> 不得 import 任一 Harness 运行时
```

失败条件含:Cordis↔legacy 相对 import、Cordis import 两个 Pi 依赖、
平台 import loop/session/prompt/tool 运行时模块、双向 SQL 提及对方会话表、
共享的 transcript/run/queue/compaction 状态类型。

### 9. Conformance 测试清单(冻结架构 §21 的全部行为)

框架行为(逐条对锁定包核对):

- 必需 inject 使 consumer 保持 PENDING,boot 审计 fail-loud;**4.0.1 没有可选 inject
  语法**——声明即硬依赖;可选依赖的约定写法是不声明 + `ctx.get()` 探测
  (写进插件作者守则);
- plugin context 读未声明的 service 抛错;root fiber 的非严格读取特例
  不被产品代码依赖;
- provider 激活启动 consumer;provider 替换使 dependents 恰好卸载并重激活一次;
- effect 精确语义:disposer 单次执行;单个 effect 内多个 disposer 逆序串行;
  多个顶层 effect 逆序并行等待;UNLOADING 期间注册新 effect 抛 `INACTIVE_EFFECT`;
  PENDING 期间积累的 effect 在 dispose 时显式排空;
- disposal 移除 listeners、services、timers、ports、子 Fiber;
- 事件模式精确语义:emit 不 await 且 listener 同步抛错传播给 emit 方;
  parallel 全部 allSettled、有 rejection 抛 AggregateError;serial/bail 的 bail 谓词为
  `v !== null && v !== false && v !== undefined`;waterfall 注册顺序由外向内、
  listener 不调 `next()` 即 veto(含内置行为)、返回值经 `next()` 双向传递;
  quirk:`parallel()` 在 `internal/dispatch` 观察者处的 mode 显示为 `'emit'`;
- isolate realm 阻止 project/session provider 泄漏;
- Loader 事务化重组四分支:无存活 fiber 直接 init(失败恢复旧配置);候选 disabled
  先 dispose 再 commit;普通 config 更新失败恢复旧 config 再试;name/inject/group
  变更先 import 新模块(旧 fiber 仍在跑)再 dispose,失败重启旧 plugin;
  group 并发 settle、失败逆序删新增并按旧序恢复;Include detached candidate →
  child tree settle → commit cache;child-tree mutation 串行 queue;写盘
  tmp+rename 与有界重试;
- 内容 reload 只影响下一个 request snapshot 并记录其 composition revision;
- 未激活/卸载中的 context 不能泄漏新 effect;
- boot 失败 dispose 部分树;
- 原始错误可观测且无隐私内容。

现成基线(移植或对照,不从零发明):

- 上游 cordis `packages/core/tests/` 的 12 个 spec(associate/decorator/dispose/
  events/fiber/invoke/isolate/logger/plugin/reflect/service/shadow),其中
  `dispose.spec.ts` 覆盖 effect 单次、逆序、async generator 中断与错误路径;
- dsh 仓库中 fork 加固的覆盖测试:`app-boot/tests/config-reload.spec.ts`、
  `hmr-config.spec.ts`、`user-patches.spec.ts`、`webserver.spec.ts`、
  `loader-composition.spec.ts`。

## 显式排除

不做:新 worker 入口(R2)、Cordis 会话表(R3)、引擎选择器(R2)、模型调用(R3)、
产品工具(R5/R6)、生产 module HMR、任意用户模块/包解析。

## 验收门槛

- conformance 套件冻结架构 §21 列出的全部基座行为;
- 有效 prompt 编辑推进 composition revision;无效编辑保留先前贡献并报告失败阶段;
- correlation 标识符跨 AsyncLocalStorage 边界传播的 fixture 通过,其丢失不改变结局;
- Pi Agent 测试与 E2E 行为不变;
- `check:fast`、focused Electron 测试、`check:package` 与打包 hybrid smoke 通过
  (新增依赖触发打包门;验证打包产物含预期 cordis 包);
- 依赖扫描证明未引入任何 DeepSeek Harness Agent 包。
