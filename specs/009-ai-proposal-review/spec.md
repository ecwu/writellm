# Feature Specification: AI 修改提案审阅

**Feature Branch**: `009-ai-proposal-review`

**Created**: 2026-07-11

**Status**: Draft

**Input**: 从原 `001-ai-writing-workspace` 拆分：逐项审阅、接受、拒绝或暂缓 AI 修改提案，并安全应用接受的变更。

## Clarifications

### Session 2026-07-12

- Q: AI 对 Block 的修改、新增、删除，在 v1 是否必须先成为提案并由作者确认后才写入正文？ → A: 所有修改、插入和删除都先生成独立提案，作者逐项或批量接受后才写入正文
- Q: AI 可以在哪个范围内提出 Block 操作？ → A: 已选 Block 的操作属于授权范围但仍走提案；范围外操作必须标记为范围扩展并由作者单独确认
- Q: AI 新增 Block 时，插入位置如何确定？ → A: AI 自行选择章节内位置；作者审阅明确位置和上下文后只能接受或拒绝，不能调整位置
- Q: 多个 AI Block 操作存在依赖时，如何接受？ → A: 独立操作逐项处理；相互依赖的操作组成原子变更组，只能整体接受或拒绝
- Q: AI 删除带有子 Block 或引用关系的 Block 时，删除范围是什么？ → A: 删除目标 Block 及全部子 Block，完整列出影响范围并作为原子变更组确认；引用无法安全处理时阻止删除

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 查看提案差异 (Priority: P1)

作为作者，我希望清楚看到原文、建议文本、变更意图和资料依据，以便在应用前做出判断。

**Why this priority**: 可理解的差异是作者控制 AI 输出的前提。

**Independent Test**: 打开包含多个变更的提案，逐项检查原文、建议文本、目标块和资料依据。

**Acceptance Scenarios**:

1. **Given** 提案已完成，**When** 用户打开任一变更，**Then** 系统区分原文和建议文本并标明目标块。
2. **Given** 变更有资料依据或证据不足，**When** 用户查看变更，**Then** 系统显示依据或需要作者判断的提示。
3. **Given** 提案包含修改、插入或删除，**When** 用户查看任一变更，**Then** 系统明确显示操作类型、目标块或插入位置，以及应用后的预期结果。
4. **Given** 提案包含新增内容块，**When** 用户审阅该变更，**Then** 系统展示 AI 选择的插入位置和相邻上下文，并只提供接受或拒绝，不提供位置调整。

### User Story 2 - 逐项处理提案 (Priority: P1)

作为作者，我希望接受、拒绝或暂不处理单个变更，以便只把确认过的内容写入正文。

**Why this priority**: 逐项控制能避免整份提案覆盖作者的手动编辑。

**Independent Test**: 对三个变更分别接受、拒绝和暂缓，确认正文只出现接受的变更。

**Acceptance Scenarios**:

1. **Given** 提案包含多个独立变更，**When** 用户接受一个变更，**Then** 只应用该变更，其他变更保持待处理。
2. **Given** 用户拒绝一个变更，**When** 操作完成，**Then** 正文不包含该建议，且拒绝状态被保留。
3. **Given** 用户暂不处理一个变更，**When** 用户离开提案，**Then** 该变更仍可在稍后继续审阅。
4. **Given** 提案包含超出任务原授权 Block 或新增位置的操作，**When** 用户处理该变更，**Then** 系统将其标记为范围扩展并要求单独确认，不得将其包含在普通批量接受中。
5. **Given** 多个变更属于同一原子变更组，**When** 用户处理组内任一变更，**Then** 系统只允许整体接受或整体拒绝该组，并展示全部受影响 Block。
6. **Given** 删除提案包含父 Block、子 Block 和引用关系，**When** 用户审阅该变更组，**Then** 系统展示完整删除树和引用影响，并且只在全部成员均可安全应用时允许整体接受。

### User Story 3 - 安全应用和恢复任务 (Priority: P1)

作为作者，我希望批量接受可安全合并的变更，并在目标正文已变化时得到提示，以便不覆盖最新手动修改。

**Why this priority**: 合并边界和过期保护决定了 AI 辅助是否可信。

**Independent Test**: 先生成提案，再手动修改目标块，打开旧提案并确认系统阻止静默覆盖；对未过期提案批量接受并验证正文。

**Acceptance Scenarios**:

1. **Given** 提案基于的目标块已被手动修改，**When** 用户尝试应用，**Then** 系统标记提案过期并要求重新确认或重新生成。
2. **Given** 用户批量接受多个变更，**When** 所有变更可定位，**Then** 正文只应用这些变更并保留任务来源。
3. **Given** AI 任务失败、取消或中断，**When** 用户返回章节，**Then** 原正文和已保存手动编辑不受影响。

### Edge Cases

- 提案变更互相冲突、重叠或无法定位时，必须要求人工判断。
- 部分接受时，剩余变更不得被静默丢弃或自动应用。
- 批量接受中某个变更失败时，系统必须明确哪些已应用、哪些仍待处理。
- 提案引用的资料已失效时，应用前必须提示作者。
- 应用变更的保存失败时，正文不得显示为已成功更新。
- 范围扩展操作不得通过“全部接受”或默认选中绕过单独确认。
- 新增 Block 的插入锚点已删除、移动到其他章节或无法唯一定位时，系统必须阻止应用并要求重新生成。
- 原子变更组中的部分操作不可应用时，整个变更组必须保持未应用或被阻止，不得产生部分写入。
- 删除变更组无法完整定位任一子 Block，或受影响引用无法安全处理时，整个删除必须被阻止。

## Scope

### In Scope

- 查看提案差异、目标块、变更意图和资料依据。
- 对内容块修改、插入和删除进行单项接受、拒绝、暂缓和批量处理。
- 过期提案检测、冲突提示和安全应用。
- 保留任务来源和审阅状态。

### Out of Scope

- AI 任务提交、执行和生成结果；由 `008-ai-writing-tasks` 负责。
- 资料导入、检索和引用创建。
- 版本时间线、任意版本比较和历史恢复。
- 自动无确认写入正文。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 展示每个提案变更的原文、建议文本、目标块和变更意图。
- **FR-002**: 系统 MUST 显示变更的资料依据或证据不足提示。
- **FR-003**: 用户 MUST 能够对单个变更执行接受、拒绝或暂不处理。
- **FR-004**: 用户 MUST 能够批量接受或拒绝仍处于待处理状态的变更。
- **FR-005**: 应用提案时系统 MUST 只改变用户接受的变更。
- **FR-006**: 部分处理后，系统 MUST 保留其他变更及其审阅状态。
- **FR-007**: 目标块版本已变化时，系统 MUST 将提案标记为过期，并在应用前要求重新确认或重新生成。
- **FR-008**: 冲突、重叠或无法定位的变更 MUST 被标记为需要人工判断，不得自动合并。
- **FR-009**: 成功应用的变更 MUST 保留对应任务、指令和资料来源。
- **FR-010**: 应用失败时系统 MUST 不得报告正文已成功保存，并提供重试或恢复操作。
- **FR-011**: 每个提案变更 MUST 明确标识为内容块修改、插入或删除；系统 MUST 仅应用作者明确接受的操作，并保持其他操作及其审阅状态不变。
- **FR-012**: 超出任务原授权内容块或新增位置的提案变更 MUST 标记为范围扩展，并在应用前获得作者单独确认；范围扩展变更 MUST NOT 被普通批量接受隐式应用。
- **FR-013**: 新增内容块的提案 MUST 展示 AI 选择的章节内插入位置和相邻上下文；作者在首版中 MUST 只能接受或拒绝该位置，插入位置无法定位或已过期时系统 MUST 阻止应用。
- **FR-014**: 相互依赖的提案变更 MUST 作为原子变更组整体接受或整体拒绝；系统 MUST NOT 允许只应用组内部分操作，且组内任一操作被阻止时整个组 MUST 不写入正文。
- **FR-015**: 删除包含子 Block 的内容块时，系统 MUST 展示目标 Block、全部子 Block 和受影响引用，并将其作为单一原子变更组处理；任何成员或引用无法安全处理时系统 MUST 阻止整个删除。

### Key Entities

- **修改提案**：等待作者审阅的变更集合。
- **提案变更**：针对一个或多个内容块的修改、插入或删除操作，包含目标、原文或插入位置、建议内容及审阅状态。
- **审阅状态**：待处理、已接受、已拒绝或暂缓。
- **范围扩展**：目标内容块或新增位置超出任务提交时授权范围的提案变更，需要独立确认。
- **插入位置**：AI 为新增内容块选择的章节内位置及其相邻内容块上下文，作者首版不直接调整。
- **原子变更组**：具有依赖关系、必须共同应用才能保持语义完整的一组提案变更。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 至少 90% 的作者能在 60 秒内指出一个提案变更的原文、建议文本和依据。
- **SC-002**: 在 100 次接受、拒绝和暂缓组合测试中，100% 的正文只包含已接受变更。
- **SC-003**: 100% 的过期提案都会在应用前被提示，不覆盖较新的手动修改。
- **SC-004**: 至少 90% 的作者能在 2 分钟内完成一次部分接受并继续编辑。
- **SC-005**: 100% 的应用失败都保留可恢复正文和明确错误状态。
- **SC-006**: 在 100 次范围扩展、原子变更组和删除子树审阅测试中，100% 的操作都经过要求的确认，且不产生未确认写入、组内部分写入或未披露的子 Block 删除。

## Assumptions

- 本 feature 依赖 `004-block-editor`、`007-source-search-citations` 和 `008-ai-writing-tasks`。
- 只有作者明确接受的变更才能进入正文。
- 成功应用的内容变更将由 `010-version-history` 记录为模型来源变更。
