# Feature Specification: 可移动项目与启动工作区基础

**Feature Branch**: `001-project-foundation`

**Created**: 2026-07-11

**Status**: Accepted

**Input**: 从原 `001-ai-writing-workspace` 拆分：创建、打开、移动项目，并在启动时提供最近项目入口与最近记录管理。

## Clarifications

### Session 2026-07-12

- Q: 001 应保存哪些工作区状态？ → A: 只保存项目身份、有效性和最近项目元数据；从 001 移除“最近编辑位置”和更广泛的工作区状态持久化
- Q: 从新位置打开项目时，如果最近列表已有相同稳定项目 ID 的记录，应如何处理？ → A: 更新原记录的位置和最近打开时间，最近列表始终只保留一条该项目记录
- Q: 成功打开或重新关联已有项目时，001 是否可以修改项目内的 manifest？ → A: 不修改项目文件；只更新应用自身的最近项目索引，manifest 的创建时间和更新时间在创建后保持不变
- Q: 创建项目时应采用哪种名称校验规则？ → A: 只遵循当前操作系统和文件系统的命名规则
- Q: 001 应如何处理用户同时启动多个应用实例？ → A: 只允许一个活动实例；后续启动请求交给已有实例处理并聚焦其窗口
- Q: 项目的最小可验证磁盘契约应采用哪种形式？ → A: 根目录包含版本化 manifest，记录稳定项目 ID、名称、格式版本及必需目录
- Q: 应用内的“删除项目”应如何处理？ → A: 不提供项目内删除选项；失效记录保留并可移除
- Q: 最近项目列表最多保留多少条记录？ → A: 最多 5 条
- Q: 失效最近记录重新选择位置时如何确认是原项目？ → A: 必须匹配原稳定项目 ID，否则拒绝关联
- Q: 无效或结构不完整的项目是否允许应用自动修复？ → A: 只显示诊断结果，不自动修复
- Q: 001 应接受 ADR-001 的范围如何划分？ → A: 拆分 ADR；项目基础由 ADR-002 负责，ADR-001 保留后续内容存储与 Git-backed history，001 不依赖或接受 ADR-001 的后续条款
- Q: 001 遇到未知 schema、未知 kind 或结构损坏时如何处理？ → A: 严格只读拒绝；仅接受 v1 有效项目，不迁移、不修复、不写回用户项目
- Q: 创建过程中应用崩溃后，临时项目目录如何处理？ → A: 临时目录永不展示；下次启动由应用尽力清理可识别的应用临时目录，清理失败只显示不含敏感信息的警告
- Q: recent index 缺失或损坏时如何处理？ → A: 缺失按空列表处理；损坏只在内存中按空列表展示并给安全 warning，成功创建或打开项目后再原子替换为有效 index
- Q: 001 应冻结怎样的能力与依赖边界？ → A: 只提供项目入口所需的最小命名能力；不包含工作区状态保存、通用通信、项目删除、任意路径或文件访问，也不新增运行时依赖
- Q: 旧的运行时信息能力应如何处理？ → A: 移除；面向用户的能力仅限 001 所需的项目入口与最近项目管理
- Q: 项目移动或重命名后，001 承诺恢复什么？ → A: 文件夹名称和路径只是存储位置；项目身份和元数据来自内部 manifest；001 恢复项目身份并进入空工作区，同时保证其他内部文件原样保留但不解析
- Q: FR-010 中“保留可恢复状态”具体指什么？ → A: 操作失败后界面可安全重试且用户可重新发起创建；不保存可续接事务；临时目录不展示并在下次启动由应用尽力清理
- Q: 项目描述是否纳入 001？ → A: 不纳入；v1 manifest 只保存稳定项目 ID、显示名称、格式版本和时间戳，项目描述及创建后元数据编辑留给后续 feature
- Q: SC-001 和 SC-004 的用户成功率指标如何验证？ → A: 保留为发布后可用性目标，不作为 001 实现完成门禁；后续通过用户研究验证

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 创建或打开项目 (Priority: P1)

作为作者，我希望创建一个可移动的 `.writellm` 项目，或打开已有项目，以便从任意位置开始写作。

**Why this priority**: 没有可靠的项目入口，后续写作内容无法被安全地拥有、保存和重新打开。

**Independent Test**: 创建项目、关闭应用、重新打开并从启动页打开该项目；整个过程不依赖其他产品功能。

**Acceptance Scenarios**:

1. **Given** 用户首次启动应用，**When** 启动完成，**Then** 系统展示新建项目和打开项目入口。
2. **Given** 用户输入项目名称并选择父目录，**When** 用户确认创建，**Then** 系统创建一个自包含项目并进入空工作区。
3. **Given** 用户选择一个项目文件夹，**When** 系统验证完成，**Then** 有效项目被打开，无效项目显示原因且不进入工作区。
4. **Given** 用户输入项目名称，**When** 当前操作系统或目标文件系统不允许该名称，**Then** 系统拒绝创建并返回明确结果；系统不额外施加跨平台名称限制。
5. **Given** 应用已有活动实例，**When** 用户再次启动应用，**Then** 启动请求由已有实例处理并聚焦其窗口，不创建第二个活动实例。

### User Story 2 - 移动后重新发现项目 (Priority: P1)

作为作者，我希望把项目文件夹移动或重命名后仍能通过打开项目恢复同一项目身份并进入空工作区，同时保证其他内部文件不被修改。

**Why this priority**: 项目必须属于作者，而不能依赖应用固定目录或旧路径。

**Independent Test**: 移动或重命名项目文件夹，再从新位置打开，确认内部 manifest 标识的项目身份保持不变、应用进入空工作区，其他内部文件保持原样。

**Acceptance Scenarios**:

1. **Given** 项目已被移动，**When** 用户从新位置选择它，**Then** 系统识别为原项目而不是新项目。
2. **Given** 项目结构不完整，**When** 用户尝试打开，**Then** 系统保留原文件、显示可理解的诊断结果且不自动修复，并提示重新选择项目。
3. **Given** 已有项目有效，**When** 用户成功打开或重新关联它，**Then** 系统只更新应用自身的最近项目索引，不修改项目内的 manifest 或其他文件。

### User Story 3 - 管理最近项目和移除最近记录 (Priority: P2)

作为作者，我希望从最近项目快速继续工作，并能主动移除失效的最近记录而不误删项目文件。

**Why this priority**: 快速回到工作现场能降低重复寻找项目的成本，同时避免误删用户文件。

**Independent Test**: 打开多个项目，重启应用，验证最近列表；打开已丢失的项目记录并移除记录，确认项目文件不会被应用删除。

**Acceptance Scenarios**:

1. **Given** 用户打开过多个项目，**When** 用户再次启动，**Then** 系统按最近打开时间展示最多 5 条项目卡片。
2. **Given** 最近项目路径已失效，**When** 用户查看启动页，**Then** 记录显示为失效，并可移除记录或重新选择位置。
3. **Given** 最近记录对应的项目文件已丢失，**When** 用户从最近列表尝试打开该项目，**Then** 系统提示文件丢失，并提供移除该最近记录的选项。
4. **Given** 最近列表已有某个稳定项目 ID 的记录，**When** 用户从新位置直接打开同一项目，**Then** 系统更新原记录的位置和最近打开时间，不创建重复记录。

### Edge Cases

- 同一父目录已有同名项目时，不得覆盖、合并或静默替换。
- 用户取消新建或打开对话框时，不创建项目、不修改最近列表。
- 最近项目被外部删除、重命名或权限不足时，不得静默删除该记录。
- 项目 manifest、必要目录或项目身份信息无效时，不得把普通文件夹当作项目打开，也不得自动修复或写入该文件夹。
- 失效最近记录重新选择位置时，如果新位置的稳定项目 ID 不匹配，不得替换或覆盖原记录。
- 创建或项目基础原子写入过程中断时，不得发布最近记录，也不得留下可被启动页识别为有效的半成品项目；用户可从启动页重新发起创建。
- 应用已有活动实例时，后续启动不得创建可并发修改最近索引或项目基础文件的第二个活动实例。

## Scope

### In Scope

- 启动页、新建项目、打开项目、最近项目和移除最近记录。
- 可移动、自包含的 `.writellm` 项目文件夹及项目身份验证。
- 空工作区的打开，以及项目名称、项目位置和最近项目元数据的保存。

### Out of Scope

- 写作动机和大纲编辑。
- 项目描述和创建后的项目元数据编辑。
- 章节、资料库、AI 任务和版本历史的产品界面。
- 远程同步、多人协作和跨项目搜索。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许用户创建、命名和打开自包含的 `.writellm` 项目。
- **FR-002**: 创建项目时用户 MUST 能够选择任意父目录，且系统不得依赖固定工作目录。
- **FR-003**: 同名项目存在时系统 MUST 阻止静默覆盖，并提供改名或更换位置的操作。
- **FR-004**: 系统 MUST 验证项目根目录版本化 manifest 中的稳定项目 ID、格式版本和必需目录结构后才允许打开项目。
- **FR-005**: 项目文件夹的名称和路径 MUST 只表示存储位置，不得作为项目身份；项目被移动或重命名后，用户从新位置打开时，系统 MUST 根据内部 manifest 恢复稳定项目身份并进入空工作区。打开或重新关联已有项目时，系统 MUST 只读验证项目目录，不得修改 manifest 或其他项目文件；其他内部文件 MUST 保持原样且不得解析其内容。
- **FR-006**: 系统 MUST 保存最近打开项目的显示摘要和最近打开时间，以稳定项目 ID 作为唯一键，并将最近列表限制为最多 5 条，按最近打开时间倒序展示。从新位置打开已有稳定项目 ID 的项目时，系统 MUST 更新原记录的位置和最近打开时间，不得创建重复记录。
- **FR-007**: 最近项目失效时系统 MUST 保留记录并显示失效状态；用户尝试打开时 MUST 提示文件丢失，并允许移除记录或重新选择项目位置。重新选择位置时，系统 MUST 仅在所选项目 manifest 的稳定项目 ID 与原记录匹配时恢复该记录；不匹配时 MUST 保留原记录不变并说明原因。移除记录 MUST 不删除项目文件。
- **FR-008**: 应用 MUST NOT 提供删除项目文件夹的项目内操作；用户只能从最近列表移除项目记录。
- **FR-009**: 取消、校验失败或存储失败时系统 MUST 返回明确结果，不得显示为成功。
- **FR-010**: 项目创建失败时系统 MUST 返回可安全重试的失败状态并允许用户重新发起创建，但 MUST NOT 持久化或续接未完成的创建事务；失败操作不得发布最近记录或留下可被启动页识别为有效的半成品项目。可识别的应用临时目录 MUST 不展示，并由应用在下次启动时尽力清理；清理失败只显示不含敏感路径或底层异常的警告。
- **FR-011**: 系统 MUST 对无效或结构不完整的项目提供诊断结果，不得自动修复或写入该项目文件夹。
- **FR-012**: 系统 MUST 只向用户界面提供完成项目入口与最近项目管理所必需的最小命名能力，并 MUST NOT 提供通用通信、项目删除、任意路径或文件访问能力。
- **FR-013**: 创建项目时，系统 MUST 只按当前操作系统和目标文件系统的规则接受或拒绝项目名称，不得额外施加跨平台保留名称或字符限制。
- **FR-014**: 系统 MUST 只允许一个活动应用实例；后续启动请求 MUST 交给已有实例处理并聚焦其窗口，不得启动可并发修改最近索引或项目基础文件的第二个活动实例。

### Key Entities

- **项目**：作者拥有的可移动工作区，包含根目录版本化 manifest、稳定项目 ID、显示名称、格式版本、创建时间和更新时间；两个时间戳在创建时写入，并在 001 范围内保持不变。
- **最近项目记录**：启动页用于快速打开项目的摘要，不代表项目正文；每个稳定项目 ID 最多对应一条记录。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001** *(post-launch outcome; non-blocking for 001 implementation acceptance)*: 后续用户研究中，至少 90% 的首次使用者能在 2 分钟内完成创建并进入空工作区。
- **SC-002**: 100% 的同名创建尝试都不会覆盖已有项目。
- **SC-003**: 在 20 次移动后重新打开测试中，100% 的有效项目能恢复原项目身份并进入空工作区。
- **SC-004** *(post-launch outcome; non-blocking for 001 implementation acceptance)*: 后续用户研究中，至少 95% 的用户能在 30 秒内从最近列表重新打开最近使用的项目。
- **SC-005**: 100% 的失效最近记录都能在启动页被识别，且移除记录不会删除对应文件夹。

## Assumptions

- 首版面向单作者和单机本地项目。
- 首版采用单活动应用实例，不支持多实例并发项目操作。
- 001 的可移动性承诺不包含项目名称的跨操作系统兼容性。
- 项目名称和 `.writellm` 后缀是用户可见的项目识别方式。
- 应用不提供删除项目文件的项目内操作；用户可在应用外部移动、重命名或删除项目文件夹，失效记录由用户主动移除。
- 无效或结构不完整的项目由应用只读诊断，用户通过重新选择有效项目处理打开失败。
- 后续 feature 会在此项目基础上写入动机、大纲、章节、资料和历史。
- 001 的项目基础存储由 ADR-002 负责；ADR-001 的内容格式、Git history 和跨内容事务
  条款属于后续 feature 的接受范围，不是本 feature 的实现前置条件。
