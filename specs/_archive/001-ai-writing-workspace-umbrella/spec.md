# Feature Specification: AI 辅助写作工作区

**Feature Branch**: `codex/v2-greenfield`

**Created**: 2026-07-11

**Status**: Draft

**Input**: User description: “我正在构建一个文章编辑器或者是写作工具。它涵盖了一个 block based 编辑器,基于 RAG 可以索引，被引用的文献资料库, 以及AI辅助生成写作和改动的功能。核心用户旅程是：创建项目 → 导入资料 → 阐明动机和列大纲 → 写一个章节 → 派遣任务请求生成 → 审阅提案 → 接受修改提案 → 完成编辑。” 追加需求：对整个项目内容提供基于 Git 或类似机制的版本控制，追踪人工和模型的全部已保存变更。

## User Scenarios & Testing *(mandatory)*

### User Story 0 - 从启动引导页进入项目 (Priority: P1)

作为作者，我希望启动软件后看到一个清晰的引导页，可以新建项目、打开任意位置的 .writellm 项目，或从最近项目中快速继续编辑，以便软件每次启动都能快速回到写作状态。

Why this priority: 项目是用户自定义位置的独立文件夹，应用不能依赖固定工作目录；启动页是发现、创建和重新打开项目的唯一入口。

Independent Test: 启动没有项目时看到新建和打开入口；创建一个项目后关闭并重启，启动页显示该项目的最近记录；移动该 .writellm 文件夹后通过打开项目重新打开，并确认项目内容不变。

Acceptance Scenarios:

1. Given 用户首次启动软件，When 启动完成，Then 系统展示欢迎/引导页，提供新建项目、打开项目和最近项目区域。
2. Given 用户点击新建项目，When 用户填写项目名称并选择任意父目录，Then 系统在该目录创建一个 <项目名>.writellm 自包含文件夹并进入工作区，不覆盖同名已有项目。
3. Given 用户已经打开过多个项目，When 用户再次启动软件，Then 启动页按最近打开时间展示有限数量的项目卡片，点击卡片即可快速打开。
4. Given 最近项目被用户移动、重命名或外部删除，When 用户启动软件，Then 该记录显示为不可用并提供移除记录或重新选择项目的位置，不得静默删除用户文件。
5. Given 用户选择打开项目，When 用户选择一个 .writellm 文件夹，Then 系统验证其 manifest 和存储结构，通过后打开项目；无效文件夹显示明确错误且不加入最近记录。

### User Story 1 - 建立项目并形成写作方向 (Priority: P1)

作为作者，我希望创建一个项目，记录写作动机并建立文章大纲，以便我知道正在写什么、为什么写以及下一步写哪一章。

**Why this priority**: 这是所有后续编辑、资料引用和 AI 辅助任务的共同上下文；没有清晰的项目目标，作者无法判断生成内容是否有价值。

**Independent Test**: 创建一个空项目，填写写作动机，增加并调整至少两个大纲条目；重新打开项目后，动机和大纲仍然可见且顺序正确。

**Acceptance Scenarios**:

1. **Given** 用户尚未创建项目，**When** 用户输入项目名称并创建项目，**Then** 系统展示该项目的工作区，并提供写作动机、大纲、正文和资料库的入口。
2. **Given** 项目已创建，**When** 用户填写写作动机、增加大纲条目并调整条目顺序，**Then** 系统保存这些内容，并能明确显示每个大纲条目是否已有对应章节。
3. **Given** 项目已有动机和大纲，**When** 用户离开后再次打开项目，**Then** 系统恢复上次保存的项目内容和当前编辑位置。

### User Story 2 - 导入 PDF、构建可检索资料并引用 (Priority: P1)

作为作者，我希望把 PDF 文献导入项目资料库，并将其解析为包含图片和内嵌表格的 Markdown，再把 Markdown 文本切成带有对应 embedding 的文本块，以便正文和 AI 任务都有可靠且可追溯的依据。

**Why this priority**: 资料库是区别于普通编辑器的核心价值，也是生成内容可信度和引用可追溯性的基础。

**Independent Test**: 导入一份包含文字、图片和表格的 PDF；确认系统保存了解析后的 Markdown 文本和配套图片、表格直接嵌在 Markdown 中，并为每个已索引文本块保存对应的 embedding。随后用关键词或自然语言检索，打开一个结果并将其作为引用插入章节；引用应能回到解析后的 Markdown 位置和原始资料位置。

**Acceptance Scenarios**:

1. **Given** 用户在项目资料库中，**When** 用户导入一份 PDF，**Then** 系统显示解析状态，并将 PDF 转换为 Markdown 文本及配套图片保存；PDF 中的表格直接保留为 Markdown 表格，而不是脱离正文的不可读附件。
2. **Given** PDF 已完成 Markdown 解析，**When** 系统执行文本切分和 embedding 计算，**Then** 每个已索引文本块都与自己的 embedding、解析后 Markdown 位置和资料来源关联保存；在这一步完成前，资料不得显示为可检索。
3. **Given** 资料已完成解析、切分和 embedding 保存，**When** 用户输入关键词或自然语言问题并执行检索，**Then** 系统返回相关文本块、资料名称、Markdown 位置和原始资料位置；结果附近的图片和表格关系仍然可查看，并允许按资料标题或标签缩小结果。
4. **Given** 用户查看一个检索到的文本块，**When** 用户将其引用到章节正文，**Then** 正文显示可识别的引用标记，引用详情包含资料名称、文本块内容或位置，并可从引用返回对应的 Markdown 片段。
5. **Given** PDF 无法读取、解析结果不完整、没有可检索文字或 embedding 计算失败，**When** 系统完成处理，**Then** 资料仍保留在资料库中并显示明确的处理阶段、失败原因和可执行的处理建议，不会被当作完整可用证据。

### User Story 3 - 以块为单位完成章节草稿 (Priority: P1)

作为作者，我希望在 block based 编辑器中专注写一个章节，并能独立调整段落和结构，以便文章结构清晰、局部修改安全。

**Why this priority**: 章节草稿是整个旅程中可以直接交付的最小写作成果，也是 AI 任务需要操作的明确范围。

**Independent Test**: 从大纲创建一个章节，添加并编辑标题、段落、列表、引用等块，移动其中一个块并保存；重新打开后，内容、顺序和引用关系均保持不变。

**Acceptance Scenarios**:

1. **Given** 用户已创建大纲条目，**When** 用户从该条目开始写章节，**Then** 系统创建一个与大纲条目关联的章节，并将编辑焦点置于正文。
2. **Given** 用户正在编辑章节，**When** 用户新增、编辑、移动、拆分、合并或删除块，**Then** 系统只改变目标块及其必要的结构关系，不改变其他章节或资料库内容。
3. **Given** 章节中已有引用，**When** 用户移动或编辑相关正文块，**Then** 引用仍保持与原资料片段的关联；若引用位置不再有效，系统明确标记需要检查。
4. **Given** 用户正在输入或刚完成修改，**When** 编辑器发生保存或用户离开章节，**Then** 系统保留最近一次已保存的正文，不因关闭或重新打开项目而丢失。

### User Story 4 - 派遣 AI 写作任务并获得提案 (Priority: P1)

作为作者，我希望针对一组明确的章节块提出生成、扩写、压缩、改写或润色请求，并指定写作意图和可用资料，以便 AI 的产出服务于我的文章，而不是替我接管文章。

**Why this priority**: 这是将资料库和写作上下文转化为实际写作帮助的关键环节；把任务限制在选定范围可降低不可控改写风险。

**Independent Test**: 选择一个或多个章节块，填写任务指令并指定资料范围，提交任务；在任务完成后，看到一份与原文并列、尚未应用的修改提案。

**Acceptance Scenarios**:

1. **Given** 用户已打开章节，**When** 用户选择一个或多个块、填写任务目标并提交 AI 任务，**Then** 系统显示任务范围、指令、使用的资料上下文和当前状态。
2. **Given** AI 任务正在执行，**When** 用户查看任务状态，**Then** 系统至少区分等待、执行中、已完成、失败和已取消，并允许用户回到正文继续手动编辑。
3. **Given** AI 任务已完成，**When** 用户打开结果，**Then** 系统展示一份提案，包含受影响的块、原文、建议文本、变更意图和相关资料引用；原正文保持不变。
4. **Given** 可用资料不足以支持任务结论，**When** AI 生成结果，**Then** 提案明确指出证据不足或需要作者判断的部分，不生成看似可靠但无法追溯的引用。

### User Story 5 - 审阅并接受修改提案 (Priority: P1)

作为作者，我希望逐项审阅 AI 提案，选择接受、拒绝或稍后处理，并在接受后继续编辑，以便最终文章始终由我控制。

**Why this priority**: 用户旅程只有在提案可理解、可控且能安全合并时才闭环；审阅是信任 AI 辅助写作的必要条件。

**Independent Test**: 对同一章节生成包含多个变更的提案，分别接受一个变更、拒绝一个变更并保留一个待处理项；确认正文只应用已接受的变更，并且资料引用未被静默删除。

**Acceptance Scenarios**:

1. **Given** 用户正在审阅提案，**When** 用户查看任一变更，**Then** 系统清楚区分原文和建议文本，并标明变更涉及的块及其资料依据。
2. **Given** 提案包含多个独立变更，**When** 用户接受、拒绝或跳过某一个变更，**Then** 系统只对该变更执行相应操作，其他变更继续保持待处理状态。
3. **Given** 用户确认接受一项或全部提案，**When** 系统应用变更，**Then** 正文更新为接受后的内容，仍保留可识别的引用关系，并记录本次应用的任务来源。
4. **Given** 用户在任务完成后已经手动修改了目标块，**When** 用户打开旧提案，**Then** 系统提示提案基于旧版本，要求用户重新确认或重新生成，不覆盖最新手动修改。
5. **Given** AI 任务失败、取消或中断，**When** 用户返回章节，**Then** 原正文和已保存的手动编辑不受影响，并可查看原因、重试或放弃该任务。

### User Story 6 - 追踪并恢复项目版本 (Priority: P1)

作为作者，我希望项目内容的每次已保存变更都能形成可追踪的版本记录，并能看出变更来自人工还是模型，以便我理解文章如何演变、比较差异并安全恢复到较早状态。

**Why this priority**: 版本历史是作者控制 AI 辅助写作、发现错误和恢复内容的基础；它必须覆盖人工编辑和已接受的模型修改，才能让提案审阅形成完整闭环。

**Independent Test**: 创建项目并写入一个章节，进行一次人工修改、接受一次 AI 提案，再进行一次人工修改；在版本时间线中确认每次已保存变更都有主体、时间、差异和来源，比较两个版本后恢复较早版本，并确认后续历史仍然可见。

**Acceptance Scenarios**:

1. **Given** 用户修改了写作动机、大纲、章节、内容块或引用关联，**When** 该修改被保存，**Then** 系统在项目版本时间线中建立一条记录，标明变更主体为人工、时间、受影响范围和前后差异。
2. **Given** 用户接受一份 AI 修改提案，**When** 提案变更进入正文，**Then** 系统建立一条标明主体为模型的版本记录，并关联 AI 任务、任务指令、受影响块和资料依据。
3. **Given** 项目已有多个版本，**When** 用户选择任意两个版本进行比较，**Then** 系统按项目、章节和内容块展示新增、删除和修改的内容，并能区分人工与模型造成的变更。
4. **Given** 用户查看一个较早版本，**When** 用户确认恢复该版本，**Then** 当前项目内容恢复到该版本的状态，同时创建一条新的人工恢复记录；恢复操作不得删除或覆盖之后的历史版本。
5. **Given** AI 提案被拒绝、任务失败或任务取消，**When** 用户查看项目版本历史，**Then** 正文版本历史不产生对应的内容修改记录，但任务历史仍保留该提案或失败信息。
6. **Given** 版本记录无法成功保存，**When** 用户尝试保存内容变更，**Then** 系统不得将变更显示为已完成保存，并向用户提供明确的恢复或重试操作。

### Edge Cases

- 用户导入重复资料时，系统应识别可能重复项并让用户决定保留、替换还是继续作为独立资料；不得静默覆盖已有资料。
- PDF 导入成功但部分页面、图片或表格无法解析时，系统应标记受影响范围；已解析的 Markdown 和图片可以查看，但不完整部分不能被伪装成完整证据。
- Markdown 表格跨越文本切分边界时，系统应保留足够的表头和表格内容，使检索结果不会变成无法理解的半张表。
- 图片没有可关联的正文位置或提取失败时，系统应保留可用的图片文件或失败状态，并明确提示其不能作为可检索文字依据。
- 资料正在解析、切分或计算 embedding 时，资料应显示当前阶段并暂不可用于完整检索；AI 任务不能把未完成资料伪装成已引用资料。
- 某个文本块缺少 embedding、来源位置或解析后的 Markdown 关联时，该文本块不得出现在可引用的检索结果中。
- 第三方 PDF 解析 API 超时、不可用、返回格式不完整或返回无法验证的内容时，系统应保留可恢复的导入状态并显示明确错误，不得把不完整结果标记为可用资料。
- 用户删除或替换被正文引用的资料时，已有引用应显示失效状态，并提供重新绑定或移除引用的选择。
- 用户提交空指令、没有选择目标块或选择的块已被删除时，系统应阻止任务提交并说明缺少什么。
- 生成结果包含与原文重叠、互相冲突或无法定位的变更时，系统应将其标记为需要人工判断，不能自动合并。
- 生成任务耗时过长、网络或服务不可用时，系统应显示可理解的状态和恢复操作，不影响当前正文编辑。
- 同一项目中存在多个章节时，AI 任务默认只作用于用户明确选择的章节和块，不得隐式修改其他章节。
- 连续输入产生的未保存瞬时状态不要求各自成为独立版本；但每一个已保存的人工或模型内容状态都必须可追踪，不能静默丢弃中间的已保存变更。
- 一次提案涉及多个块时，批量接受的变更应作为一条清晰的版本记录呈现；部分接受只能记录实际接受的变更。
- 恢复历史版本后再次编辑时，系统应保留恢复前后的完整时间线；首版不要求提供分支合并或冲突解决。
- PDF 重新解析、文本重新切分或 embedding 重新计算属于资料处理事件，应与资料关联并可追踪，但不能被误标为人工或模型对文章正文的修改。
- 如果旧版本引用的资料已被删除或替换，恢复时应标记失效引用并要求用户重新绑定或移除，不得静默指向另一份资料。

## Scope

### In Scope

- 启动引导页，提供新建项目、打开已有项目和最近项目快速打开。
- 用户选择任意父目录创建自包含的 <项目名>.writellm 文件夹；项目移动后可通过打开项目重新发现。
- 单作者项目工作区，包括项目名称、写作动机、一个文章大纲和多个章节。
- 支持段落、标题、列表、引用和资料引用等常用内容块的章节编辑。
- 章节正文以可被普通工具打开的 Markdown 文件作为 canonical content，并保留可恢复 block/citation identity。
- 仅导入 PDF，并将其解析为包含配套图片的 Markdown 文本；PDF 中的表格直接嵌入 Markdown。
- 对解析后的 Markdown 文本进行切分，为每个文本块计算并保存对应 embedding，完成后按文本块检索可引用片段。
- 将资料片段作为可追溯引用插入正文，并在引用失效时提醒作者。
- 针对选定章节块提交 AI 写作或修改任务，查看任务状态，审阅提案并逐项或批量接受、拒绝。
- 为 AI 提案保留原文、建议文本、变更范围和资料依据，保障作者对最终正文的控制。
- 为项目写作内容提供可按时间查看的版本历史，追踪人工和模型变更，比较任意两个版本，并以非破坏方式恢复历史版本。
- 将资料解析、切分和 embedding 处理事件与对应资料关联，避免与文章正文修改混淆。

### Out of Scope

- 多人实时协作、评论权限、团队空间和版本审批流程。
- 自动抓取网页、自动购买或下载付费文献，以及代替用户确认版权或引用合规性。
- 自动发布、投稿、排版为特定出版社格式，以及完整的参考文献样式管理。
- 让 AI 在没有作者确认的情况下直接写入或覆盖正文。
- 超出本地项目工作区的跨项目统一资料库。
- 远程仓库同步、多人合并、分支管理、冲突解决和面向开发者的 Git 操作界面。
- 自行开发 PDF 解析引擎；首版使用第三方 PDF 解析 API。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 允许用户创建、命名、打开和删除一个自包含的 .writellm 文件夹项目；创建时用户 MUST 能够选择项目的父目录。
- **FR-036**: 系统 MUST 在启动时展示引导页，提供新建项目、打开已有项目和最近项目快速打开入口；首次启动没有最近项目时 MUST 提供清晰的空状态。
- **FR-037**: 系统 MUST 将新项目创建为用户选择目录下的 <项目名>.writellm 文件夹；同名文件夹存在时 MUST 阻止静默覆盖并提供改名或更换位置的操作。
- **FR-038**: .writellm 文件夹 MUST 自包含项目 manifest、写作内容、资料、AI 任务和历史记录；项目被移动或重命名后，用户通过打开文件夹仍 MUST 能够恢复项目内容。
- **FR-039**: 系统 MUST 在启动页保存最近打开项目的路径、显示名和最近打开时间，并将不可用路径标记为失效；移除最近记录 MUST 不删除项目文件。
- **FR-040**: 系统 MUST 在打开任意文件夹时验证其 .writellm manifest、项目 ID、schemaVersion 和必需目录；验证失败 MUST 返回明确错误且不得加入最近项目。
- **FR-002**: 系统 MUST 为每个项目提供写作动机、文章大纲、章节正文和资料库四类可区分的工作内容。
- **FR-003**: 用户 MUST 能够新增、编辑、删除和重新排序大纲条目，并将大纲条目关联到一个章节或标记为尚未开始。
- **FR-004**: 章节编辑器 MUST 支持至少标题、段落、列表、引用和资料引用五类内容块。
- **FR-005**: 用户 MUST 能够新增、编辑、移动、拆分、合并和删除内容块；这些操作 MUST 不改变未选中的章节或资料。
- **FR-006**: 系统 MUST 在用户编辑后保存项目内容，并在项目重新打开时恢复最近一次已保存的动机、大纲、章节、块顺序和引用关系。
- **FR-007**: 系统 MUST 只允许用户将 PDF 文件导入当前项目的资料库，并为每份资料保存可识别的来源信息和处理状态。
- **FR-008**: 系统 MUST 将导入的 PDF 解析为 Markdown 文本和配套图片保存；PDF 中的表格 MUST 直接嵌入 Markdown 文本，图片 MUST 与其在解析后资料中的位置保持可关联。
- **FR-009**: 系统 MUST 将解析后的 Markdown 文本切分为可检索的文本块，并为每个文本块计算和持久化一个对应的 embedding；文本块、embedding、解析后位置和来源信息 MUST 可以作为同一资料记录关联读取。
- **FR-010**: 系统 MUST 区分解析、切分、embedding 计算、可检索、部分失败和失败等处理状态；只有完成所需处理且同时具有文本块、embedding 和来源位置的内容，才能显示为可检索和可引用。
- **FR-011**: 系统 MUST 对已完成处理的资料提供关键词和自然语言检索，并返回相关文本块、资料名称、解析后 Markdown 位置及原始资料位置；文本块附近的图片和 Markdown 表格关系 MUST 仍可查看。
- **FR-012**: 系统 MUST 允许用户为资料添加标签或备注，并按资料名称或标签筛选检索结果。
- **FR-013**: 系统 MUST 允许用户把检索到的文本块插入章节作为引用；每个引用 MUST 能显示资料名称、文本块内容或位置，并能返回资料库中的对应 Markdown 片段。
- **FR-014**: 系统 MUST 明确区分可用、处理中、部分失败和失败的资料状态；不可用资料 MUST 不能被标记为 AI 任务的已引用依据。
- **FR-015**: 用户 MUST 能够选择一个或多个目标内容块、填写任务指令、选择可用资料范围并提交 AI 生成或修改任务。
- **FR-016**: 系统 MUST 展示每个 AI 任务的目标范围、指令、资料上下文、状态和结果；状态至少包括等待、执行中、已完成、失败和已取消。
- **FR-017**: AI 任务完成后，系统 MUST 生成独立于当前正文的可审阅提案，不得在用户确认前自动改变正文。
- **FR-018**: 每份提案 MUST 说明受影响的内容块、原文、建议文本、变更意图和可追溯的资料依据；没有充分依据的内容 MUST 被标记为需要作者判断。
- **FR-019**: 用户 MUST 能够对提案中的每个变更执行接受、拒绝或暂不处理，也 MUST 能够在确认后批量接受或拒绝剩余变更。
- **FR-020**: 系统 MUST 在应用提案时只改变用户接受的变更，保留被拒绝或暂不处理的变更，并保留任务来源以便作者理解正文变更来由。
- **FR-021**: 如果提案基于的目标块已被用户手动修改，系统 MUST 将提案标记为基于旧版本，并在应用前要求用户重新确认或重新生成。
- **FR-022**: AI 任务失败、取消或中断时，系统 MUST 保留正文和已保存的手动编辑，并提供查看原因、重试或放弃任务的操作。
- **FR-023**: 系统 MUST 在用户提交缺少目标块、指令或有效资料范围的 AI 任务前给出阻止提交的明确提示。
- **FR-024**: 系统 MUST 在资料被删除或替换后，将受影响的正文引用标记为失效，并允许用户重新绑定或移除该引用。
- **FR-025**: 系统 MUST 对 AI 请求使用的正文和资料范围进行可见提示，并只发送用户明确选择的内容和完成任务所需的资料上下文。
- **FR-026**: 系统 MUST 提供用户可理解的错误信息和恢复操作；任何 PDF 解析、切分、embedding 计算或 AI 处理失败都不能静默丢失正文、引用、解析后的 Markdown、图片或项目结构。
- **FR-027**: 系统 MUST 为项目中所有已保存的写作内容变更建立版本记录，至少覆盖写作动机、大纲、章节、内容块、引用关联和用户接受的 AI 提案。
- **FR-028**: 每条版本记录 MUST 标明变更主体为人工、模型或系统，记录时间、变更摘要、受影响范围、前一版本和可查看的前后差异。
- **FR-029**: 人工保存写作内容后，系统 MUST 将该变更记录为人工版本，并允许用户从记录回到受影响的项目、章节或内容块。
- **FR-030**: 用户接受 AI 提案后，系统 MUST 将实际应用的变更记录为模型版本，并关联对应的 AI 任务、任务指令、受影响块和资料依据；被拒绝、失败或取消的提案 MUST 不得改变正文版本历史。
- **FR-031**: 系统 MUST 提供项目版本时间线，并允许用户按时间和变更主体浏览版本，比较任意两个版本的项目、章节和内容块差异。
- **FR-032**: 用户 MUST 能够将整个项目或指定范围恢复到较早版本；恢复 MUST 创建一条新的人工版本记录，且不得删除、覆盖或隐藏恢复前已经存在的历史版本。
- **FR-033**: 一次批量接受涉及多个内容块的 AI 提案时，系统 MUST 将实际接受的变更作为一条可识别的模型版本记录；部分接受 MUST 只记录被接受的变更。
- **FR-034**: 如果版本记录无法保存，系统 MUST 不得向用户报告内容变更已成功保存，并 MUST 保留当前可恢复内容及明确的重试或恢复操作。
- **FR-035**: 系统 MUST 将 PDF 解析、文本切分、embedding 计算和重新索引等资料处理事件与对应资料关联记录，并明确标注这些事件不是人工或模型对文章正文的修改。
- **FR-041**: 系统 MUST 将章节正文保存为 Markdown 文件；内容块和引用关联 MUST 使用可验证的稳定标识保存，外部 Markdown 修改造成标识缺失或重复时 MUST 提示作者检查。
- **FR-042**: 系统 MUST 在项目内部 Git repository 中为每个成功保存的人工或已接受模型正文变更创建 commit，并通过可解析的 metadata 区分主体、事件、项目 revision、AI task 和 proposal；Git commit 失败时 MUST 不报告保存成功。

### Key Entities *(include if feature involves data)*

- **项目**：作者围绕一篇文章组织的独立工作区，包含写作动机、大纲、章节、资料库和 AI 任务记录。
- **写作动机**：作者对文章目标、读者、问题和预期结果的简要说明，用于作者自检并作为后续任务上下文。
- **大纲条目**：文章结构中的一个主题或章节计划，可关联一个章节并记录完成状态。
- **章节**：由内容块组成的文章局部，属于一个项目并可对应一个大纲条目。
- **内容块**：章节中的最小可编辑内容单元，拥有内容类型、正文、顺序和相关引用。
- **资料**：用户导入项目的 PDF 及其解析后的 Markdown 文本、配套图片、来源信息、标签、备注和处理状态。
- **资料块（Chunk）**：从解析后的 Markdown 文本切分出的可检索文本单元，包含文本内容、来源位置及与对应 embedding 的关联。
- **Embedding**：一个资料块对应的可持久化检索表示，用于发现相关资料块；它必须能回到原始资料块和解析后的 Markdown 位置。
- **资料片段**：资料块及其相关的 Markdown 表格、图片或上下文位置，可以被查看和引用。
- **引用**：正文与资料块或资料片段之间的可追溯关联，包含显示方式和有效性状态。
- **AI 写作任务**：针对指定内容块、作者指令和资料范围的一次生成或修改请求，包含状态和结果。
- **修改提案**：AI 任务产生的待审阅变更集合，包含原文、建议文本、变更范围、依据和审阅状态。
- **版本记录**：项目内部 Git repository 的一次 commit 及其 WriteLLM metadata，包含变更主体、时间、摘要、前一版本、受影响范围和前后差异。
- **变更主体**：产生或触发变更的参与者类型，包括人工、模型和系统；人工与模型主体必须能被用户区分。
- **资料处理事件**：资料解析、切分、embedding 计算或重新索引等系统事件，与资料处理状态和结果关联，但不代表文章正文被修改。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在首次使用测试中，至少 90% 的作者能够在 15 分钟内完成“创建项目 → 导入一份资料 → 填写动机和大纲 → 写出一个章节草稿”的主流程。
- **SC-002**: 对一份不超过 20 页、包含文字、图片和表格的可读取 PDF，至少 95% 的导入操作能在 60 秒内显示“可检索”或明确的失败原因；处理中的资料必须始终显示当前处理阶段。
- **SC-003**: 100% 的显示为可检索的文本块都同时具备已保存的 embedding、解析后 Markdown 位置和资料来源；缺少任一项的文本块不得出现在可引用检索结果中。
- **SC-004**: 在包含 500 份已完成处理资料的项目中，至少 90% 的有效检索请求能在 5 秒内返回至少一个带资料名称、文本块和原文位置的相关结果；没有相关结果时应明确告知用户。
- **SC-005**: 100% 的已完成 AI 任务都提供可独立审阅的提案；提案在用户确认前不得改变正文，并且至少 95% 的提案能显示受影响块、原文、建议文本和资料依据或“无充分依据”提示。
- **SC-006**: 在可用性测试中，至少 90% 的作者能够正确地接受一个变更、拒绝一个变更并保留一个待处理变更，且最终正文只包含已接受的变更。
- **SC-007**: 在正常关闭并重新打开项目的测试中，至少 99% 的已保存动机、大纲、章节块顺序、引用关系、解析后的 Markdown 和资料处理状态保持一致；任何未保存状态必须向用户明确提示。
- **SC-008**: 至少 80% 的试用作者在 5 分制问卷中给出不低于 4 分的评价，认为“资料引用和 AI 提案让我更容易完成一个章节，同时仍能控制最终文字”。
- **SC-009**: 100% 的已保存人工或已接受模型内容变更都能在项目版本时间线中找到对应记录，并显示变更主体、时间和受影响范围；模型变更还必须关联对应 AI 任务。
- **SC-010**: 在可用性测试中，至少 90% 的作者能在 60 秒内比较任意两个版本，并正确指出至少一处差异及其来自人工还是模型。
- **SC-011**: 在恢复测试中，100% 的历史版本恢复操作都会生成新的人工版本记录，且恢复前后的所有历史版本仍可浏览和比较。

## Assumptions

- 首版面向单一作者在桌面工作区中完成一个项目；不包含实时协作、团队权限或跨项目检索。
- 项目不是由应用固定存储在单一 documents root；用户在创建时选择父目录，项目本身是可移动的 <项目名>.writellm 文件夹。
- 应用只在自己的 userData 目录保存最近项目索引和 UI 偏好；最近项目索引丢失不应损坏 .writellm 项目。
- 最近项目路径可能因用户移动、重命名、外部删除或权限变化而失效；软件显示失效状态并允许移除记录或通过打开项目重新绑定。
- 首版只允许导入本地 PDF；Markdown 文本和图片是 PDF 解析后的保存产物，不是用户直接导入的资料格式。
- PDF 解析由第三方 API 提供；该 API 负责将 PDF 转换为包含配套图片和内嵌 Markdown 表格的 Markdown 产物，产品负责调用、验证返回结果、保存产物、跟踪状态并处理失败，不自行实现 PDF 解析器。
- embedding 以切分后的 Markdown 文本块为单位计算和保存；首版不要求为图片单独计算视觉 embedding，但图片必须与其附近的 Markdown 内容保持关联。
- AI 服务已经由产品或用户配置可用；本规格只定义任务、上下文、提案和审阅行为，不定义具体模型或服务提供商。
- AI 请求可能需要将用户选择的正文和资料片段发送给配置的 AI 服务；产品必须在请求前明确显示范围，并遵循项目的隐私与安全约束。
- 引用以资料名称、原文片段和位置为基本可追溯信息；完整参考文献格式和出版级排版不属于首版范围。
- 章节内容以用户明确保存的版本为准；任何 AI 输出都先作为提案存在，作者确认后才会进入正文。
- 版本控制机制对用户表现为项目版本历史；首版使用项目内部 Git repository，commit metadata 区分人工、模型、系统事件和正文变更，且不包含远程同步。
- “追踪所有变更”指所有成为已保存项目内容的人工或模型变更；未保存的瞬时输入不需要单独生成版本记录。
- AI 提案只有在被接受并写入正文后才成为模型版本；被拒绝、失败或取消的提案保留在任务历史中，不成为正文版本。
- 恢复采用非破坏的线性历史模型；首版不包含分支、合并、远程同步或多人冲突解决。
- 资料解析、切分、embedding 和重新索引的变更以资料处理事件追踪，不复制为每一次文章版本的正文变更。
- 规格只描述产品行为和用户价值；持久化方式、检索策略、进程边界和具体 AI 集成方式在后续计划及必要的架构决策记录中确定。
